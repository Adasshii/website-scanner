# Phase 3 — UI Design Contract

> Visual and interaction contract for the admin Shortlist surface. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Baseline rule:** `app/admin/page.tsx` IS the de-facto design system for this project. No component library, no design tokens file, no shadcn. Every value below is extracted from that file (StatCard, TabButton, ScansTable, LeadsTable, StatusBadge) or from `components/scan/issue-card.tsx`'s severity-chip language, never invented fresh. This is a single-tenant internal tool (PROJECT.md: "not a product") — clarity and low ceremony over polish.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-gray-50` (page background) + `bg-white` (cards/table surface) | Page background, table/card surfaces |
| Secondary (30%) | `bg-adashi-gulf` (`#001D4E`, header bar) + `text-gray-400`/`text-gray-500` (labels, secondary text) | Header bar, table headers, secondary copy |
| Accent (10%) | `bg-adashi-blue` (`#006DFF`) | Reserved for: the active Shortlist tab button, the Release button, the cutoff slider's filled track/thumb (`accent-color`), links (domain → live site), focus rings (already global via `*:focus-visible`) |
| Destructive | `red-600`/`red-700` on `red-50` background (e.g. `text-red-600`, `bg-red-50`) | Gate-row marker background tint, "GATED" badge, unreachable/no-HTTPS chips only. Never used for the Release action itself — Release is a spend action, not a destructive one, and must stay visually distinct from delete/reject actions |

Accent reserved for: the active tab pill (`bg-adashi-blue text-white`, matches `TabButton`), the Release CTA button, the cutoff slider's active track (`accent-adashi-blue` on the native `<input type="range">`), and the domain hyperlink color (`text-adashi-blue hover:underline`, matches every existing domain link in `ScansTable`/`LeadsTable`). Do not spend accent blue on chips, badges, or gate markers — those use the severity palette below, kept separate so the one true accent color stays legible as "the actionable thing."

**Signal-severity palette (new for this phase, but reused from `components/scan/issue-card.tsx`'s existing `severityStyles` convention — not invented):**

| Tier | Classes | Used for |
|------|---------|----------|
| Critical / gate | `bg-red-100 text-red-700 border-red-200` | "GATED" badge, Unreachable chip, No HTTPS chip |
| Major | `bg-orange-100 text-orange-700 border-orange-200` | No-viewport chip, heavy-page chip (>3MB or truncated), slow-response chip (>4000ms), long-redirect-chain chip (≥4 hops) |
| Minor | `bg-yellow-100 text-yellow-700 border-yellow-200` | Moderate-weight chip (1-3MB), moderate-response chip (1500-4000ms), short-redirect-chain chip (2-3 hops) |
| Info | `bg-blue-50 text-blue-400 border-blue-100` | Robots-blocked chip (informational, not a fault) |

Score-tier text color (already established in `ScansTable`/`LeadsTable` for `scan.scores.overall`, reused identically for `triage_score.score`): `text-green-600` (≥80), `text-yellow-600` (50-79), `text-red-600` (<50). **Note the inversion:** full-scan scores are "higher = better," but the triage score research (§03-RESEARCH.md, "Proposed default weighted-score bands") defines triage score as "0-100, LOWER = worse" to mirror `lib/scoring.ts`'s direction — so the same three-tier color thresholds apply, but read the same way visually (green = healthy/high, red = bad/low) since triage's "healthy" end is also the high end of its own scale. No re-interpretation needed; the number-to-color mapping is identical to the existing `ScansTable` code.

## Shortlist Table Contract (TRI-07)

**Columns**, in order:

| Column | Content | Notes |
|--------|---------|-------|
| (marker) | "GATED" badge or blank | Only rendered when `triage_score.gated === true`; empty cell otherwise — do not render an empty badge/placeholder, keep the column narrow (`w-8`-style, matches the existing checkbox column width pattern) |
| Domain | `{domain}` as a link, `text-adashi-blue hover:underline font-medium`, `target="_blank"`, opens `https://{domain}` | Identical pattern to `ScansTable`'s domain cell |
| Triage score | `{score}` in `font-bold`, color per the score-tier rule above | For gated rows, still render the numeric score (research: "still computed for display consistency") but visually de-emphasize it slightly relative to the GATED badge — the badge is the primary signal for gated rows, the number is secondary |
| Signals | `SignalChips` component — a wrapped row (`flex flex-wrap gap-1`) of the applicable chips: Unreachable, No HTTPS, No viewport, Heavy page, Slow response, Long redirects, Robots blocked. Render only the chips that apply (a clean fast site shows zero chips — don't pad with "OK" pills) | Directly satisfies D-02: "the shortlist shows why a prospect ranks badly" |
| Released | "Released {relative date}" in `text-gray-400 text-xs`, or blank if not yet released | Blank (not "—") when not released, matching the codebase's existing dash-for-empty convention elsewhere but avoiding a third visual language — a genuinely blank cell reads fine here since the "Released" column heading already frames it |

**Sort/row order:** `ORDER BY gated DESC, score ASC` (worst-first, gated rows always first) — this is a display-layer contract on top of the query research already specifies; no UI decision needed beyond rendering in the order the data arrives.

**Gate-row visual distinction (D-01 — "not just a high number"):**
- `border-l-4 border-red-400` on gated rows (left stripe, matches no other existing pattern in this codebase but is the smallest addition that reads as "structurally different row," not just a color change dependent on the score column alone)
- `bg-red-50/30` row background tint (subtle, keeps table scannable — not full-saturation red, which would fight with the chip colors)
- The "GATED" badge (marker column, see above) as the non-color-dependent signal (accessibility: a colorblind user still sees the text badge)

**Released rows:** `opacity-60` (visually recede, matches the general convention of "already handled" fading, though this is new to this codebase — closest precedent is `StatusBadge`'s muted `bg-gray-50 text-gray-500` for a `pending` state). Released rows still appear in the table (never removed from view — Joshua needs to see what already went out) but sink toward the bottom of visual attention despite worst-first sort, since they're excluded from the eligible/cutoff calculation entirely (D-06/D-09).

## Cutoff Control Contract (TRI-08)

**Control type: slider (native `<input type="range">`).** This is not an open design question — CONTEXT.md's own wording locks it ("so Joshua slides it and watches eligibility re-shuffle instantly," D-03) and RESEARCH.md's recommended default (`score <= 60`, 0-100 range) fits a range input directly. A numeric input is not offered as an alternative; do not re-litigate.

**Spec:**
- `min={0} max={100} step={5}`, default value = 60 (research's recommended starting cutoff)
- `accent-adashi-blue` (native range-input accent color, zero extra CSS, matches the one-accent-color rule above)
- Full-width on mobile (`w-full`), fixed reasonable width on desktop (matches the existing admin's `max-w-6xl` container discipline — the slider does not need its own max-width, the page container already bounds it)
- Live readout directly above or beside the slider, updated on every `onChange` (client-side re-filter of already-fetched rows — D-07, zero network round-trip per slide): **"Cutoff: score ≤ {value} — {eligibleCount} of {totalTriaged} eligible"**
- Direction label: since triage score is "lower = worse" (mirrors `lib/scoring.ts`), the slider's semantic is "include everything scoring at or below this line." Label the two ends of the track explicitly to avoid ambiguity: left end "0 (worst)" / right end "100 (best)" as small `text-xs text-gray-400` captions under the track — this is the one piece of UI copy this phase adds beyond the Copywriting Contract table, because getting the direction backwards would silently invert who gets scanned

**Live re-shuffle behavior:** Moving the slider recomputes and re-renders the `eligibleCount` StatCard and re-sorts/re-highlights table rows (gated rows always shown as eligible regardless of slider position, per D-01) — all client-side against already-fetched `triage_score` data, no API call. This is the on-screen demonstration TRI-08 exists to provide.

## States

| State | Trigger | Treatment |
|-------|---------|-----------|
| Loading | Tab switch / initial fetch | Reuses existing `<div className="p-12 text-center text-gray-400">Loading...</div>` verbatim — matches `ScansTable`/`LeadsTable`'s shared loading cell |
| Empty (nothing triaged) | `total triaged === 0` | Empty-state copy from Copywriting Contract, centered, same `p-12 text-center` container pattern as "No scans yet." |
| None eligible at cutoff | `eligibleCount === 0` and `totalTriaged > 0` | Table renders with zero rows below the StatCards; empty-state copy inline in the table body area (not a full-page state — StatCards and slider stay visible so Joshua can immediately drag the slider to fix it) |
| All eligible already released | `eligibleCount === 0` because everything eligible has `scan_released_at` set | Distinct copy from "none eligible" (see Copywriting Contract) — tells Joshua the real reason, doesn't make him guess whether the cutoff or the release history is the cause |
| Releasing (in-flight) | Release button clicked, POST in flight | Button shows "Releasing..." and is disabled, matches `BulkDeleting`'s existing `{bulkDeleting ? "Deleting..." : ...}` pattern in `ScansTable` |
| Release success | POST 200 | Re-fetch shortlist data (same `onDelete`-style refresh-callback pattern already used after bulk delete); no toast/banner library exists in this codebase — a brief inline confirmation text ("Released {N}.") for ~3s is acceptable, or simply let the refreshed table/StatCards be the confirmation (ASSUMPTION: prefer the latter — matches this admin's existing "no toast library" reality rather than introducing one for a single button) |
| Release failure | POST non-200 | `alert("Failed to release prospects.")` — matches the exact existing pattern (`alert("Failed to delete scan.")` / `alert("Failed to delete lead.")`) |

## Release Action Contract (TRI-09, D-04, D-05, D-06, D-11)

- Button label and confirmation copy: see Copywriting Contract table above.
- **Disabled when:** `eligibleCount === 0` (nothing to release) or a release is already in flight.
- **Confirmation is mandatory** (`window.confirm`, matching the codebase's only existing confirmation pattern) and must show, before any request fires: the count that will actually be released (`min(eligibleCount, ceiling)`), the ceiling value, and — only when `eligibleCount > ceiling` — the overflow note explaining the rest roll into the next run (D-05: "nothing is lost," this must read as reassurance, not data loss).
- The Release button itself never uses the destructive-red palette (that's reserved for delete/reject elsewhere in this admin) — it uses the accent blue, since spending scan budget is the intended, positive action of this screen, not a hazard to visually warn against. The warning lives in the confirmation copy, not the button color.
- After a successful release, released prospects immediately reflect `scan_released_at` in the table (opacity-60 treatment, excluded from `eligibleCount`) without a full page reload — re-fetch and re-render only.

## Accessibility & Responsive

- **Keyboard:** the native `<input type="range">` cutoff slider is keyboard-operable by default (arrow keys adjust value) — no custom slider component, no extra work needed, and this is itself a reason the slider choice is cheap to build correctly. The Release button and table row links are standard focusable elements; the project's existing global `*:focus-visible { outline: 2px solid #006dff; outline-offset: 2px; }` (already in `app/globals.css`) applies to all of them with zero new CSS.
- **Color is never the only signal:** the "GATED" text badge (not just row-tint) and each signal chip's text label (not just its background color) both carry the actual meaning — a colorblind user reading only the text sees the same information as a sighted user reading only the color.
- **Responsive parity with the existing admin:** the shortlist table wraps in `overflow-x-auto` exactly like `ScansTable`/`LeadsTable` (the codebase's established mobile-table strategy — horizontal scroll on narrow viewports, not a card-collapse redesign). The StatCards grid uses the existing `grid-cols-2 sm:grid-cols-4` breakpoint unchanged. The cutoff slider is `w-full` so it never overflows on mobile. Do not build a new responsive pattern for this one tab — match what the other two tabs already do, so the three tabs feel like one admin, not three different admins glued together.
