<objective>
Wire the whole own-site path together: carry the profile slice in the existing scan request, harvest
inside the scan that is already running, aggregate the pages into one site-level result, and store
it in one readable column.

Purpose: this is where success criterion 2 becomes true, and where D-9-13's whole point pays off.
The scanner needs profile parameters, and the two ways to give it them are a build edit or a request
field. The build edit is exactly the change two v1.0 quick tasks found could break the Railway build
or its boot with nothing looking wrong, so the slice travels in the request and neither build file
is touched.

Output: migration 023, the slice on the request contract, the harvest hook, the aggregator, the
second best-effort update, the retention entry, and a blocking human checkpoint to apply the
migration before the scanner deploys.
</objective>

<surfaced_planner_assumptions>
## Surfaced planner assumptions (spec-less edge-probe fallback)

The ENG-01, ENG-02 and ENG-05 probe items are authored in plans 09-05 and 09-07 where the
extractors live. Two planner decisions specific to this plan were discretionary and are recorded so
they can be argued with:

- **Storage shape: one new jsonb column on `scans`, not a new table and not inside
  `scans.pages[].data`.** The third option needs no migration and is already covered by the
  existing `pages` anonymisation, but the facts are site-level while `pages` is per page, so every
  reader would re-aggregate, and `PageData` is persisted so the raw harvest would bloat it. A new
  table is heavier than a one-to-one value needs and would also have to join the retention table
  allowlist. The column wins on Joshua's own readback requirement: one column, one query. The cost
  is one additive migration and the deploy-order hazard the blocking checkpoint and the second
  update both address.
- **The per-page harvest is deliberately not persisted.** It travels on
  `ScanPageResultWithScreenshot`, the carrier the screenshot buffers already use, which is
  explicitly not stored. Only the aggregated facts and the per-trade score map reach the database.
  If a later phase wants the raw harvest for debugging, that is a new decision with its own
  retention consequences, not an omission here.
- **The stored shape is versioned at `schemaVersion: 1`.** Phases 10 through 12 read it and will
  want to evolve it. Without the version, a reader cannot tell which producer wrote a row, and the
  only safe change would be an additive one forever.
</surfaced_planner_assumptions>
