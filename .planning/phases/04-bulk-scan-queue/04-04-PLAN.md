<objective>
Wire the libraries into three thin routes and one cron schedule: the paced drain tick, the human-gated "Run batch" arming action, and the human-gated re-queue of a failed prospect.

Purpose: D-07 splits the decision from the pacing — the human decides when scan budget is spent, the machine handles the rate. These routes are that seam. Each is a gate plus one library call, following Phase 3's `app/api/admin/release-prospects/route.ts` precedent.
Output: three routes with their existing-pattern auth gates, a fourth `vercel.json` cron entry, and no queue logic living inside a route handler.
</objective>

  <action>
    Create `app/api/cron/drain-scan-queue/route.ts` as a GET handler mirroring `app/api/cron/follow-up/route.ts` wherever the pattern applies.

    Auth first, before creating any Supabase client: read the `authorization` header and compare against `Bearer ${process.env.CRON_SECRET}`, returning 401 when the env var is missing or the header does not match. Fail closed when `CRON_SECRET` is unset.

    Then, in this order:
    1. `reconcileInFlightScans(supabase)` — settle whatever finished since the last tick, so the visible status is never more than one tick stale (SCAN-03) and so freed capacity is observed before new work is claimed.
    2. `claimNextScanBatch(supabase, BULK_BATCH_SIZE)` — the atomic claim. The route takes no input at all; the batch size comes from the constants module, never from the request. The RPC also clamps its own argument, so the bound holds even if a caller-supplied size is ever introduced later.
    3. `dispatchClaimedProspects(supabase, claimed)` — bounded, paced dispatch.
    4. Return `NextResponse.json({ reconciled, claimed, dispatched, refused, skipped })` — aggregate counts only. No prospect domains, URLs or ids in the response body.

    Set `export const runtime = "nodejs"` and `export const maxDuration = 60`, matching the existing crons. Add a comment in the `send-pending-reports` style explaining that the route dispatches and returns without awaiting any scan: `full-async` is fire-and-forget, so a tick's duration is bounded by robots pre-flights and dispatch spacing, not by scan time (Pitfall 4).

    Wrap the body in the standard try/catch, logging with the `[cron/drain-scan-queue]` prefix and returning a generic 500. A claim error is logged server-side and returned as a generic 500 without echoing the raw Postgres error to the caller.

    Then add a fourth entry to the `crons` array in `vercel.json`: path `/api/cron/drain-scan-queue`, schedule `*/10 * * * *`. Ten minutes at a batch size of 2 drains a full 20-prospect armed batch in under two hours, comfortably inside the 10-50 prospects/week scale. Overlapping ticks are safe by construction: the claim is SKIP LOCKED and an over-capacity dispatch is refused and requeued rather than queued behind a timeout.
  </action>

    The library call is `armBatch(supabase)`. Return `NextResponse.json({ armed: ids.length })`. The arming ceiling is `BULK_ARM_CEILING` from the constants module and is never accepted from the request body — the server owns the ceiling, exactly as `RELEASE_CEILING` is owned in the release route. If a `ceiling` field is present in the body, validate it as a finite number between 1 and `BULK_ARM_CEILING` and reject anything else with a 400; a value above the constant is clamped down, never up.

    Comment the route with D-07: this arming write is what makes the human gate structural. The drain only claims rows whose `scan_status` is `queued`, so a prospect released by Phase 3 but never armed here is never scanned. A pure cron drain would let a mis-set cutoff quietly turn into 20 real scans with nobody in the loop.

    Create `app/api/admin/requeue-scan/route.ts` as a POST handler with the identical auth gate. It reads a single `id` field from the body, validates it is a non-empty string that parses as a UUID before any database call, and calls `requeueProspect(supabase, id)`. Return `NextResponse.json({ requeued: true })`. Comment it with D-05 and SCAN-04: this is the only path from `failed` back to `queued`, it is human-triggered, and `requeueProspect` itself filters on `scan_status = 'failed'` so this route can never resurrect a prospect that is done or in flight.

    Both routes use the shared catch shape from the release route: capture the message, log it with a route-named prefix, and return `{ error: <human message>, detail: msg }` with status 500.

## Trust Boundaries
