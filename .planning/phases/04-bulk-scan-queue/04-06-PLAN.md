  <action>
    Create `scripts/check-public-scanner-health.ts` following `scripts/triage-prospects.ts`'s CLI conventions.

    It computes the public scanner's rolling success rate: over the trailing `PUBLIC_SCANNER_BASELINE_DAYS` window, count `scans` rows where `prospect_id is null` and `status = 'completed'`, divide by the count of `scans` rows where `prospect_id is null` over the same window, and print the rate to one decimal place alongside both raw counts and the exact window boundaries. Restricting to `prospect_id is null` is what keeps bulk failures out of the metric — the number being watched is the public scanner's own rate, never a blend.

    Support two modes:
    - `--save <label>` writes the computed reading to a small JSON file under `.planning/phases/04-bulk-scan-queue/scan-health/<label>.json` containing the rate, both counts, the window bounds and an ISO timestamp. This is the baseline capture.
    - `--compare <label>` recomputes now, prints the saved reading beside the current one, prints the delta in percentage points, and exits 0 when the current rate is no more than `PUBLIC_SCANNER_TOLERANCE_PP` percentage points below the saved one, or exits 1 when it has dropped further. A rise is always a pass.

    With no flags it prints the current reading and exits 0.

    Print every number rather than only the verdict, so Joshua eyeballs the raw counts himself — the human-in-the-loop philosophy D-07 sets for the rest of the phase applies to its verification too. Keep the tolerance and window in the constants module; do not inline either value here.

    Add an npm script `"scanner-health": "tsx scripts/check-public-scanner-health.ts"` alongside the existing `triage` script.
  </action>
  <verify>
    <automated>npx tsc --noEmit && npm run scanner-health && npm run scanner-health -- --save phase04-baseline && npm run scanner-health -- --compare phase04-baseline</automated>
  </verify>
