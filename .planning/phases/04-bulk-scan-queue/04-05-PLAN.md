<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser admin UI → admin API routes | The shared admin secret is held in client state and sent as a header on each mutation |
| Public internet → `/report/[id]` | Prospect reports are readable by anyone holding the URL |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-17 | Elevation of Privilege | Run batch and Re-queue clicks | high | mitigate | Both POST through routes that check `x-admin-secret` server-side; the client component never decides authorisation, it only forwards the header, and both actions require an explicit `window.confirm` before firing |
| T-04-18 | Information Disclosure | `/report/[id]` reachable without auth | medium | accept | D-12 is a deliberate, recorded tradeoff: the cold email links to the report as proof and an auth or email gate there kills the pitch. Unguessability rests on the existing `gen_random_uuid()` scans id, the same control the public scanner has always relied on. Phase 4 introduces no new exposure — it reuses `/report/[id]` verbatim per D-11 |
| T-04-19 | Information Disclosure | failure reasons rendered in the admin table | low | accept | `scan_status_reason` holds internal error text and is shown only behind the admin secret gate, never on any public surface |
</threat_model>
