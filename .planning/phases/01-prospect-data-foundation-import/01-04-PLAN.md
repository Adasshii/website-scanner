  <action>
    Implement lib/overture-client.ts per RESEARCH Pattern 2. Export
    `queryOverturePlaces(params: OvertureQueryParams)` where OvertureQueryParams is
    { country: string; region?: string; category: string; limit?: number }. Create an
    in-memory DuckDBInstance, `INSTALL spatial; LOAD spatial; INSTALL httpfs; LOAD httpfs;`,
    `SET s3_region='us-west-2';`. Hardcode the Overture release as a documented constant
    (OVERTURE_RELEASE, e.g. "2026-06-17.0") with a comment to bump it manually — do NOT add
    release auto-discovery (Open Question #3). Read from
    `s3://overturemaps-us-west-2/release/${OVERTURE_RELEASE}/theme=places/type=place/*`.

    Runtime category detection (Pitfall 1): before building the WHERE clause, run a
    `DESCRIBE SELECT * FROM read_parquet(<path>) LIMIT 0` (or catch a column-not-found
    error) via a `detectCategoryColumn(conn)` helper to determine whether the current
    release exposes `categories.primary` or `taxonomy.primary`/`basic_category`, and filter
    on whichever is populated — never hardcode one. Select and reduce each row to
    OverturePlaceRow: id AS gersId, names.primary AS name, `websites?.[0]` reduced to
    websiteUrl (websites is a LIST and often empty — absence is the no-website path,
    Pitfall 2), addresses[1].country/.region, the detected category column, confidence.
    Filter WHERE addresses[1].country = params.country, optional region, and the detected
    category column = params.category. Apply LIMIT when params.limit is set.

    Note the known trade-off in a comment: struct-field predicates on addresses[] may prune
    row groups less effectively; a bbox pre-filter is the documented escalation only if a
    real run proves too slow — do not build it now.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Overture-sourced URL (untrusted) → dry-run reachability fetch | Arbitrary third-party URLs from an external dataset are fetched during the dry-run sample |
| Overture row data (untrusted) → importer → DB | Third-party fields drive per-row writes under the service-role key |
| SUPABASE_SERVICE_ROLE_KEY in a local script | The importer runs locally with full DB privilege |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-06 | Tampering / Information Disclosure (SSRF) | dry-run reachability fetch of Overture websites[0] | high | mitigate | Route every Overture-sourced URL through `validateUrlSafe()` (DNS resolution + private-IP/metadata block) before any HEAD/GET; never a bare fetch(). A failing URL is reported blocked, not fetched. Covered by the private-IP fixture test. |
| T-01-07 | Denial of Service (self-inflicted) | one malformed Overture row aborting the whole batch | medium | mitigate | Per-row try/catch that logs the gersId + error and continues; the batch never crashes on a single bad row (project "fail gracefully" convention). |
| T-01-08 | Elevation of Privilege | SUPABASE_SERVICE_ROLE_KEY exposure via the local script or its logs | high | mitigate | Load from .env/.env.local via the existing dotenv pattern; never hardcode or log the key; .env is gitignored (existing project control). |
| T-01-09 | Tampering (data quality) | untrusted Overture rows imported at scale without review | high | mitigate | D-11 blocking-human sample audit before the first real import; --dry-run is write-free; runtime category detection prevents a silently-empty category filter. |
| T-01-SC | Tampering | @duckdb/node-api / tldts already installed (plan 01-02) | high | transfer | Legitimacy verified at install time in plan 01-02's blocking-human checkpoint; no new install here. |
</threat_model>
