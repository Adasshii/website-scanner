# Phase 04.1 Plan 01: Releasability Gate (Predicate + Wiring + Batch Size) Summary

**Single isReleasable() predicate excludes food-service categories and unreachable prospects from selectWorstN while keeping no-HTTPS reachable prospects top-priority, plus BULK_BATCH_SIZE raised 2→10 for the daily drain cadence.**

## Accomplishments
- `EXCLUDED_CATEGORIES` configurable list (Overture eat-and-drink family) + `isExcludedCategory()`/`isReleasable()` pure functions in a new `lib/triage-eligibility.ts`, unit-tested for every behavior case in the plan
- `selectWorstN` (lib/triage-release.ts) now selects `category` and filters via `isReleasable` instead of the old inline `gated || score <= cutoff` check — food-service and unreachable prospects can no longer be released, no-HTTPS prospects still sort first
- `getShortlist` (lib/triage-candidates.ts) now selects `category` on `ShortlistRow` so Plan 02's UI can call `isReleasable` without a second query; `getTriageCandidates` intentionally unchanged (excluded/unreachable rows stay visible in the shortlist, only barred from release)

## Decisions Made
- Category exclusion mechanism: read-time filtering via a pure predicate (Claude's Discretion per CONTEXT.md), not import-time filtering or a backfill/re-triage — existing already-triaged rows are handled without touching the scorer or re-running triage.
- Seeded `EXCLUDED_CATEGORIES` with 18 Overture "eat and drink" `categories.primary` strings (restaurant, cafe, bar, pub, coffee_shop, fast_food_restaurant, bakery, bistro, brasserie, pizza_restaurant, cafeteria, food_court, ice_cream_shop, diner, wine_bar, tea_room, snack_bar, pancake_restaurant) per the plan's exact seed list — flagged in-comment as a starting set to confirm against real data at Plan 02's checkpoint (per CONTEXT.md Claude's Discretion note).
- `isReleasable` takes `{ triage_score, category }` and a `cutoff` — matches the plan's exact signature so `selectWorstN`'s existing `ReleaseCandidate` shape (id, triage_score, category) satisfies it directly.
