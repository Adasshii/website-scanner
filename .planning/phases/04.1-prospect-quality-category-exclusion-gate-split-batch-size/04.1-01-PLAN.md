<objective>
Build the read-time releasability gate that makes the shortlist feed the pipeline the right businesses before Phase 5: food-service categories and unreachable sites become non-releasable, no-HTTPS sites stay top priority, and the daily drain takes a bigger bite.

This plan is the backend/logic half (no UI, no deploy): a single releasability predicate plus its data-layer wiring and the batch-size constant. Plan 02 consumes the predicate in the admin UI and ships everything live.

Purpose: One authoritative eligibility rule (isReleasable) so the server release path and the UI can never drift. Existing already-triaged rows are handled at read time — no re-triage, no migration — because every triaged row already stores reachable/https, and every imported row already stores category (prospect-upsert.ts sets prospects.category from place.category).

Output: EXCLUDED_CATEGORIES constant (D-4.1-02), lib/triage-eligibility.ts, selectWorstN + getShortlist wired to it, BULK_BATCH_SIZE = 10 (D-4.1-06).

Deliberate non-change: lib/triage-scorer.ts is NOT modified. The D-01 gate split (D-4.1-03/04) lives in the consumers (eligibility predicate + UI), not the scorer — the stored gated boolean stays valid, so no re-triage is required.
</objective>
