# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** this phase's only UI surface is (1) a 5th admin tab, "Reporting" (TRK-03/04/05),
and (2) one new column on the existing Shortlist tab (TRK-01/02, D-7-14). Retention
(CMP-13/14/15) is a headless monthly cron with no admin UI — CONTEXT.md's locked decisions
never ask for a retention panel, and none is specified here (see "Explicitly out of scope"
below). This is presentation over data that already exists; no new interaction patterns, no
new component primitives, no shadcn.

---

| Property | Value |
|----------|-------|

## Copywriting Contract

No i18n keys. This project's public pages (`report`, `scan`, `start`) use `next-intl` with
namespaced keys — but the admin surface is explicitly zero-i18n by prior, logged decision
(STATE.md, Phase 3: *"no next-intl on the admin surface (matches existing zero-i18n admin
convention)"*), confirmed by grep: `messages/en.json` has no `admin` namespace at all. This is
a single-tenant tool Joshua alone operates; every existing admin string (`"Loading..."`,
`"No scans yet."`, `"Failed to fetch shortlist"`) is hardcoded English. This spec follows that
established convention rather than the generic bilingual instruction, because "match what's
already there" and the zero-i18n admin decision are both explicit and binding.

| Element | Copy |
|---------|------|
| Primary CTA | None. The Reporting tab is read-only by design (D-7-11/12) — no release, approve, or delete action exists here, so there is no CTA to specify. |
| Tab label | `Reporting` (5th entry in the `Tab` union, alongside `scans` / `leads` / `shortlist` / `outreach`) |
| Empty state heading (zero prospects ever) | `No prospects imported yet` |
| Empty state body (zero prospects ever) | `Run the importer to start building your funnel.` |
| Empty state heading (prospects exist, zero activity in the 30-day window) | `No activity in the last 30 days` |
| Empty state body (prospects exist, zero activity in the window) | `Every date below reads zero. Check the Shortlist tab to see where existing prospects currently stand.` |
| Error state | `Failed to load reporting data{: {detail}}.` on non-401 failure; `Could not connect to server.` on network failure — verbatim reuse of `fetchShortlist`/`fetchOutreach`'s existing copy pattern, noun swapped to "reporting data" |
| Destructive confirmation | Not applicable — no destructive action exists on this tab |
| "Not yet sending" — per-day table cell (Reply rate / Booked columns) | `— Not yet sending` (`text-gray-400 italic text-xs`) |
| "Not yet sending" — funnel/summary explainer (shown once, above the per-day table, only while the global gate is open) | `Reply rate and booked calls aren't measurable yet — outreach sending is a later phase (Phase 8). Once the first message sends, these numbers take over on their own.` |

**Gate for "Not yet sending":** a single global boolean — has any `outreach_messages` row ever
reached `status = 'sent'`? While false, every day's Reply rate and Booked cells (and the
explainer line) render the awaiting-copy above instead of a number, per D-7-13. The moment it
flips true, all cells render real per-day numbers with no further UI change — this is a read-
time gate, not a stored flag, matching D-7-01/D-7-10's "derive, don't store" pattern.

**Deliberately narrower than "broken vs. absent vs. zero":** the phase brief for this tab asks
the UI to distinguish absence from breakage. This spec resolves exactly what CONTEXT.md's D-7-13
locks — "not yet sending" (Phase 8 hasn't shipped) vs. a real number — because that is the one
distinction Phase 7 has the data to make honestly. It does **not** add a "pipeline broken"
indicator for Reply rate/Booked, because once Phase 8 ships, Phase 7 has no signal to tell a
genuinely-zero reply rate apart from a broken webhook; that diagnostic belongs to Phase 8's own
health monitoring, not to this reporting surface. Imported/Triaged/Scanned/Contacted counts need
no such treatment at all — they are plain per-day row counts derived from markers that already
exist (D-7-10), never ambiguous, and a zero on a given day (e.g., no import ran) is just an
honest zero rendered as `0`, no special copy.

| E4 | error | ✅ covered | Inherits the Shortlist table's existing error banner. State is derived from the same payload, so the column cannot fail independently of the table. |
| E4 | populated | ✅ covered | One pill per row from the 12-value vocabulary, using the fine-state colour mapping in the Color section. |
| E4 | partial | ✅ covered | Derivation is total: every prospect resolves to exactly one of the 12 states with `new` as the floor (D-7-02). No row renders a blank, `unknown`, or placeholder pill. |
| E4 | overflow | ✅ covered | Fixed short uppercase labels inside the Shortlist table's existing `overflow-x-auto` wrapper; the column adds no new overflow behaviour. |
| E4 | zero-one-many | ✅ covered | Exactly one pill per row, always. No singular/plural copy and no count-dependent layout. |
| E4 | long-text | ✅ covered | Fixed vocabulary; longest label is `SCAN QUEUED` (11 chars). No truncation or wrap handling needed, matching the existing `NAMED-PERSON` / `CRITICAL` pills. |

**Why the two `partial` rows are `backstop` and not plain truths.** They carry D-7-13's honesty
guarantee, and their failure mode is silent: if the sent-gate logic regresses, the UI renders a
plausible `0%` reply rate, which is precisely the "number that looks like a result and is
actually an absence" D-7-13 exists to prevent. A code-reading verification would pass such a
regression. These two require explicit test evidence — a held-out UI-state test asserting the
awaiting treatment with the gate closed and real numbers with it open. At verify time, absent
that evidence they route to `insufficient_spec → human_needed` rather than passing silently.

**Explicitly out of scope (not a gap):** a retention/CMP-13-15 admin panel. CONTEXT.md's
locked decisions describe retention as a headless monthly cron (`/api/cron/retention`) whose
`RETENTION_MODE=dry-run` output is a log/response payload, not an admin-visible view. Claude's
Discretion in CONTEXT.md does not ask for one, and the phase brief explicitly warns against
inventing one. None is specified.

**Lifecycle pill placement on Shortlist (D-7-14):** a new dedicated `Stage` column, placed
between the existing `Status` (bulk-scan `scan_status`: queued/scanning/done/failed) and
`Released` columns — not stacked into the existing priority-pill cell (`CRITICAL` /
`UNREACHABLE` / `NAMED-PERSON`). Those pills answer "is this row a priority to scan" and "is the
contact risky to auto-mail"; the new `Stage` pill answers a different question, "where is this
prospect in the funnel" — keeping them in separate columns matches the codebase's existing
per-concern column separation (`Status` = queue engineering state, `Signals` = triage chips,
first column = priority/risk flags) rather than overloading one cell with unrelated pills.
