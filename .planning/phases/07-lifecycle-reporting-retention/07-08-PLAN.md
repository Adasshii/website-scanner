<objective>
Close FA-CMP-13-SOURCES: decide, on the record, what anonymise mode does with `prospect_sources`,
then make the codebase say so in a way a test enforces.

Purpose: verification scored criterion 4 `partial` for two reasons, and this is the second one.
`lib/retention.ts` and `lib/retention-constants.ts` do not reference `prospect_sources` anywhere —
confirmed by grep, returning 0 in both files. Migration 011 stores `raw_name`, `raw_address` and
`raw_website_url` per prospect, keyed by `prospect_id`. Anonymise mode nulls
`prospects.name/domain/website_url/address` and leaves those three columns sitting one join away
from the prospect they describe. Delete mode is unaffected: the `ON DELETE CASCADE` on
`prospect_sources.prospect_id` clears them correctly as a side effect.

D-7-17 makes anonymise the default the moment `RETENTION_MODE` is ever set. That is the whole
argument for closing this now rather than later: the gap costs nothing while the job is in dry-run
and becomes the job's primary failure mode on the first writing run. This plan does not set that
variable and does not deploy.

What is genuinely undecided here is a compliance question, not an engineering one, which is why
Task 1 is a blocking decision rather than an implementation instruction. The sharpest form of it is
not the three text columns — those are trivially nullable. It is `overture_gers_id`: not null,
unique, and a stable pointer into Overture's public dataset that resolves back to the real business.
While it survives, the pass is pseudonymisation, whatever the three text columns say.

Output: a recorded decision in `07-DECISION-RECORD.md`, the code that implements it, and an
integration test that pins it so a future reader cannot quietly reopen it.
</objective>

  <context>
    **The facts, before the options.**

    Migration 011 stores one row per Overture record that contributed to a prospect:
    `raw_name`, `raw_address`, `raw_website_url`, `raw_category`, `raw_region`, `raw_country`,
    `raw_confidence`, `overture_gers_id`, `overture_release`, and three timestamps.
    `prospect_id` is `on delete cascade`, so delete mode already clears these rows correctly and
    nothing below changes that. Anonymise mode never opens the table at all.

    Today, after an anonymise pass, `select p.id, ps.raw_name, ps.raw_address, ps.raw_website_url
    from prospects p join prospect_sources ps on ps.prospect_id = p.id` returns the business name,
    street address and website URL that the pass was supposed to erase. That is a one-line join, not
    a reconstruction attack.

    **The part that is not solved by nulling three columns.** `overture_gers_id` is `not null` and
    `unique`. It cannot be nulled in place, and it is a stable public identifier: it resolves to the
    business's own record in the Overture Maps dataset, from which the name and address are readable
    again. So as long as a `prospect_sources` row survives, the pass is pseudonymisation, not
    anonymisation, however many text columns are cleared. Whether that distinction matters here is a
    legal judgment, which is why this is a decision and not a task.

    **The re-import interaction, which cuts the other way.** `overture_gers_id` is IMP-03's
    idempotency key. Under option A the row survives, so a later import of the same region matches
    it and re-populates `raw_name`/`raw_address`/`raw_website_url` — and, depending on how
    `upsertOverturePlace` writes through, potentially the anonymised prospect's own columns too.
    Read that module before answering; if it does write through, anonymisation under option A is
    undone by the next import of the same region, which is a material argument for option B. Under
    option B the row is gone, so a re-import creates a fresh prospect rather than matching the
    anonymised one — correct minimisation, at the cost of a duplicate prospect row whose only
    remaining link to the old one is nothing at all.

    **What is not decided here:** the 12-month window. It is a placeholder pending the LIA (D-7-R3)
    and stays `RETENTION_MONTHS`. Nothing below changes it.

    **What this decision gates:** `RETENTION_MODE` is unset and stays unset. This decision is
    required *before* it is ever set to `anonymize`, which is D-7-17's default. It is not a
    prerequisite for the dry-run deploy in plan 07-10, and 07-10 does not set the mode either.
  </context>
