<flagged_assumptions>
## Flagged assumptions — phase roster

`07-SPEC.md` does not exist, so the deterministic edge probe was run over the 8 phase
requirements instead. Five requirements returned `unclassified` and are surfaced here rather than
auto-dismissed. Each is repeated in the plan that owns it; this is the complete roster.

- **FA-TRK-02 (plan 07-02).** The derivation is fresh only because nothing caches it. No test
  asserts that no caller memoises the derived stage, so TRK-02's "advances as real events happen"
  guarantee would degrade silently the first time someone adds a cache in front of
  `deriveLifecycleState()`. Unverified.
- **FA-TRK-04 (plan 07-05).** The domain-fallback match uses `.maybeSingle()`, which throws when
  more than one row matches. `prospects_domain_unique_idx` (migration 010) is unique on non-null
  `domain`, so multiple matches are believed impossible — but that index is partial, and the
  behaviour has not been exercised against a real multi-row set.
- **FA-TRK-05 (plan 07-03).** "Imported" counts `prospects.created_at`, which fires once per
  prospect at first import. A re-import that touches an existing prospect contributes nothing to
  that day's count. Whether Joshua reads "imported per run" as first-seen or as touched-by-a-run
  is unresolved by CONTEXT.md.
- **FA-CMP-13 (plan 07-07).** That `0 3 1 * *` deploys and actually fires monthly on Vercel Hobby
  is established from Vercel's documentation only, not from an observed run on this project.
  `07-VALIDATION.md` records it as the phase's single manual-only verification.
- **FA-CMP-15 (plan 07-06).** `suppressions` has no foreign key to `prospects` (verified against
  migration 014), so no cascade can reach it. What is unresolved is the tension the requirement
  itself creates: `suppressions.email` is personal data that CMP-15 requires be kept forever,
  while CMP-13 expires personal data everywhere else. Nothing in CONTEXT.md, the ROADMAP, or the
  requirements resolves whether a future "anonymise the suppression email too" reading would be
  compliant or would break suppression matching. Not resolved here; flagged for the LIA.
</flagged_assumptions>
