<objective>
Deliver the retention job's config surface, its selection query and its scheduled entry point, end to
end, in the one mode that cannot destroy anything: dry-run.

Purpose: CMP-13 asks for a scheduled job that expires prospect, scan and outreach data. The half of
that requirement which decides whether the job is correct is not the DELETE — it is the clock. D-7-18
says so outright: dry-run exists because it "is what catches an off-by-one in D-7-15's clock
expression before it anonymises 800 rows." So this plan builds and proves the clock, the scope
boundary and the config that drives them, wires them to a real cron route, and stops there. Nothing
in this plan can write a row.

That split is not tidiness. D-7-16 records retention's reversibility as one-way: a wrong scope or a
wrong window is not undoable from the application, and this repo's `.env.local` points at the REMOTE
production Supabase, so a job run locally runs against production data. Keeping every writing path
out of this plan means a reviewer reading it does not have to trust a mode branch to know it is safe
— there is no branch that writes.

It also closes the phase's second structural requirement. CMP-15 is what ROADMAP.md line 337 calls
the trap of this phase, and D-7-19 is explicit that a comment is not the control: "A comment tells
the next person; the test stops them." So the table allowlist here is not a documented list, it is
the only way this module is allowed to name a table — one guarded accessor, a union type derived
from the list, and a runtime check for the case where someone casts past the compiler.

Output: `lib/retention-constants.ts`, `lib/retention.ts` (selection plus the dry-run arm),
`GET /api/cron/retention`, and the two integration suites that prove the clock, the scope and the
allowlist against a real Postgres.

Why wave 5 rather than wave 1: retention has no data dependency on any earlier plan in this phase —
it does not read `prospects.booked_at`, the lifecycle derivation, or anything the reporting surface
produces, and its `files_modified` set is disjoint from all five written plans. The ordering behind
07-05 is the shared local Supabase instance that every `*.integration.test.ts` in this repo runs
against, recorded in `07-VALIDATION.md` § Test Infrastructure (`fileParallelism: false`, "do not run
`npm test` in parallel shells") and in this project's standing one-executor-at-a-time convention.
Two plans seeding prospect fixtures into one database at the same time corrupt each other; parallel
waves would buy nothing here and cost that.
</objective>

    Export `type RetentionMode = "anonymize" | "delete" | "dry-run"`.

    Export `const RETENTION_MODE: RetentionMode`, resolved by validating `process.env.RETENTION_MODE`

    Security Domain's V5 row requires this value be validated against the closed enum at read time
    rather than trusted as a free-form string, and the cast would pass anything through. Note in a
    comment that the fallback direction is deliberate and one-way: an unreadable value must resolve to
    the mode that writes nothing, never to one that writes.

    Export `const RETENTION_MONTHS: number`, resolved from `process.env.RETENTION_MONTHS` through
    `Number()`, accepted only when it is a finite integer of at least 1, otherwise 12 with a
    `console.warn`. Comment that 12 is CMP-13's placeholder pending the LIA and not a legal fact
    (D-7-R3), that it is config precisely so counsel's answer changes this value and no code, and that
    D-7-15's deferred second window for never-contacted prospects would arrive as a sibling constant
    here rather than as a redesign.

    Export `const RETENTION_TABLE_ALLOWLIST = ["prospects", "outreach_messages", "scans"] as const`
    and `type RetentionTable = (typeof RETENTION_TABLE_ALLOWLIST)[number]`. Carry the "never add X
    here" comment style already used for `EXCLUDED_CATEGORIES` in `lib/triage-constants.ts`: state
    that the suppression table is deliberately absent and can never be added, that suppression rows
    key on email independently of any prospect row and must survive every retention pass permanently,
    that removing one recreates exactly the re-contact risk suppression exists to prevent (CMP-15),

    (D-7-19). Also state that `leads` is absent for the same class of reason: it belongs to the public
    scanner, which D-7-R5 puts outside this job's blast radius.

    Export `const RETENTION_MAX_BATCH = 1000` with a comment recording what it is for: PostgREST caps
    an unbounded select at its own default page size, so a run that silently processed only the first
    page would expire a partial set and report a number that looked complete. The selection asserts
    against this cap instead of paging. At 10 to 50 prospects per week (D-7-R4) a single monthly run
    reaching 1000 expiring prospects is not reachable; if it ever is, someone must look, and the
    upgrade path is to page the candidate query rather than to raise this number.

    Export `async function selectExpiringProspects(sb: SupabaseClient, cutoffIso: string): Promise<ExpiringProspect[]>`:

    1. Candidate read. Through `retentionFrom`, select `id, created_at, latest_scan_id` from the
       prospects table filtered `.lt("created_at", cutoffIso)` and bounded

       approximation: the clock is a maximum over a set that always contains `created_at`, so a
       prospect created after the cutoff cannot possibly have a clock before it. Throw when the
