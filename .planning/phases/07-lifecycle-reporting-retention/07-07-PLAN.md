<objective>
Give the retention job its two writing modes, put it on the monthly schedule, and stop one deliberate
step short of pointing it at production data.

Purpose: plan 07-06 proved the clock and the scope while being structurally unable to write. This plan
adds the writes. Anonymise is the default that matters — D-7-17 chose it over delete precisely so the
funnel history TRK-05 is built on in this same phase survives the expiry of the personal data beside
it. Delete is the alternative, and it is the one with a real schema hazard behind it: migration 013
added two foreign keys with no `ON DELETE` clause that reference each other, so the obvious delete
order raises a foreign-key violation against real data and nowhere else. `07-RESEARCH.md` found that
cycle by reading the migration; this plan pins it with a test that asserts the naive order actually
fails, because "the job completed without throwing" is not evidence that the ordering is what made it
work.

CMP-15 finishes here. Plan 07-06 made the suppression table unreachable; this plan proves the row
survives a run in every mode, including the one that deletes. `07-VALIDATION.md` lists that assertion
among the two things in this phase that fail silently and must not be accepted on code inspection, and
D-7-19 is blunt about why: "A comment tells the next person; the test stops them."

What this plan does not do is turn it on. D-7-18 is explicit — ship in dry-run, read one run's output,
then flip it. D-7-16 records this job's reversibility as one-way: a wrong scope or a wrong window is
not undoable from the application. So the last task is a decision, not a deploy step, and Joshua makes
it holding a production dry-run's own counts rather than a plan's assurance that the numbers should be
right.

Output: `anonymizeProspects()` and `deleteProspects()` in `lib/retention.ts`, the three field-list
constants that define what anonymisation actually clears, the completed `lib/retention.integration.test.ts`,
the fifth `vercel.json` cron entry, and a blocking decision on whether the mode flips.
</objective>

    Count the outreach rows first, through `retentionFrom` on the outreach table selecting `id` filtered

    takes the outreach rows with it. Record that this hazard is invisible in a dry-run, because a SELECT
    never trips a foreign key, which is why it needs a test of its own.

    Record the non-atomicity plainly rather than implying a transaction: these are three separate
    PostgREST calls and nothing spans them. A failure between steps leaves prospects whose
    `latest_scan_id` is already null and whose scans are already gone; the next monthly run re-selects
    them, since anonymisation and deletion of scans do not move the clock, and completes. Self-healing
    is the claim; atomic is not.

    Do not reach for a stored procedure or an RPC to get atomicity. The two retention functions defined
    in `supabase/migrations/001_create_scans_and_leads.sql` at lines 43 and 51 are dead code that
