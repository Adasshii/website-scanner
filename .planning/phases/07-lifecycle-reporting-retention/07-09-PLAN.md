<objective>
Fold in the two code-review warnings this phase left open: the unchunked `.in()` in `getShortlist()`
and the two-row candidate cap in booking attribution.

**Scope call, recorded explicitly.** Neither of these is a verification gap — criterion 4 is the
only failed truth and neither of these touches it. Both are folded in rather than deferred, for
reasons that differ:

- **WR-02 is folded in because it is a recurrence, not a discovery.** Plan 07-06 hit exactly this
  query shape against this project's own 711-row local `prospects` table and got PostgREST's
  "URI too long". The fix, the chunk size, and the reasoning are already written down in
  `lib/retention-constants.ts`. `getShortlist()` builds the identical shape with no chunking over a
  set that grows with every triaged prospect. Leaving a known, already-solved failure mode in a
  second call site is the definition of a broken window, and it takes the Shortlist tab down
  outright when it fires — along with the Stage column (TRK-01) that reads the same query result.
- **WR-01 is folded in because it fails silently and crosses an external trust boundary.** It needs
  3+ prospects sharing a `contact_email`, which is uncommon at 10-50 prospects a week but is an
  ordinary data state, not an anomaly — `contact_email` carries no unique index and shared
  `info@` mailboxes are exactly what the extractor collects. When it fires it does not crash: it
  writes `booked_at` on the wrong prospect, or reports `no_sent_outreach` for a real booking. Both
  become numbers on the Reporting funnel that look like results. That is the same class of
  silent-wrong-answer D-7-13 rejects elsewhere in this phase.

Neither is deferred. Both are cheap, both have their fix already written in the review, and both sit
in code this phase authored.

Purpose beyond the two fixes: `chunkIds` currently exists once, unexported, inside a module whose
import has side effects (`lib/retention-constants.ts` resolves `RETENTION_MODE` and can
`console.warn` at module scope). Importing the retention module into the admin read path to reuse one
six-line pure function would couple the Shortlist page to the retention job's config resolution for
no reason. One tiny dependency-free module, imported by both, costs one file and removes that.

Output: `lib/chunk-ids.ts` with its unit test, a chunked `getShortlist()`, an uncapped and correctly
disambiguated `attributeBookingToProspect()`, and integration coverage for the 3-candidate case that
was previously untested.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Fillout webhook (public internet) -> `POST /api/webhooks/fillout` -> `attributeBookingToProspect()` | An externally-supplied email address selects which internal prospect row gets written. The address is attacker-controllable in principle and uncontrolled in practice. |
| admin browser -> `GET /api/admin/shortlist` -> `getShortlist()` -> PostgREST | Authenticated internal surface, but the request URL it builds is a function of row count rather than of anything the caller supplies. |
| application -> PostgREST gateway | The URL length limit is enforced at the gateway, outside this codebase, and produces a hard error rather than a truncated result. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

Takes out the Shortlist tab and the Stage column together. Mitigated by chunking at `SHORTLIST_ID_CHUNK_SIZE`, with a multi-chunk integration test asserting every row still returns. |
| T-07-09-02 | Tampering | `attributeBookingToProspect()` email step | high | mitigate | With 3+ prospects sharing a `contact_email`, a capped candidate query can return two ungated rows while the genuinely gated prospect falls outside the fetched set — writing `booked_at` on the wrong prospect or reporting no booking at all. `booked_at` feeds both the lifecycle `booked` rung and the Reporting funnel's Booked card, so the wrong answer is presented as a fact. Mitigated by removing the pre-gate cap and deciding ambiguity from the post-gate set, with integration tests at 3 candidates covering the gated, ambiguous and ungated outcomes. |

| T-07-09-SC | Tampering | npm/pip/cargo installs | — | accept | This plan adds no dependency. `files_modified` contains no manifest or lockfile. No package-legitimacy checkpoint is required because no install occurs. |
