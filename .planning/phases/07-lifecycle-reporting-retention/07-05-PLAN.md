<objective>
Deliver TRK-04: a booking that lands on the Fillout form attributes to the prospect it came from, so
"booked calls attributable to outreach" is a real number rather than a column that exists.

Purpose: the Fillout webhook already marks `leads` as booked and has done since migration 004. It
knows nothing about `prospects`. Plan 07-01 added `prospects.booked_at` and
`prospects.booked_match_method`; plans 07-02 and 07-03 built the funnel card and the per-day Booked
column that read them. Nothing writes them yet. This plan is the writer, and it is the only one the
codebase will have.

It is also where FA-TRK-04 gets closed rather than inherited. `07-RESEARCH.md`'s Pattern 2 sketch
resolves both lookups with a single-row Supabase terminator, which throws when the database returns
more than one row. `prospects_domain_unique_idx` (migration 010, lines 37-40) makes that impossible
for the domain probe — it is a partial unique index on non-null `domain`, and the probe value is
never null. But `prospects.contact_email` carries no unique index of any kind (migration 010 line 31
declares a plain `text` column, and the only unique indexes on the table are the domain one and
`suppressions`' own), so two prospects sharing a mailbox is an ordinary data state, not an anomaly.
This plan makes both lookups bounded array queries and resolves a multi-candidate set through the
D-7-08 sent-gate the design already requires — so the crash cannot happen, and the misattribution
the crash was hiding cannot happen either, at the cost of zero extra queries.

Output: `lib/booking-attribution.ts`, one guarded post-step inside `POST /api/webhooks/fillout`, and
the route-level integration test `07-VALIDATION.md` lists as a Wave 0 requirement.

Why wave 4 rather than wave 1: the only data dependency is migration 019 (plan 07-01). The ordering
behind 07-04 is the shared local Supabase instance that every `*.integration.test.ts` in this repo
runs against, recorded in `07-VALIDATION.md` § Test Infrastructure (`fileParallelism: false`, "do not
run `npm test` in parallel shells") and in this project's one-executor-at-a-time convention.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Fillout -> `POST /api/webhooks/fillout` | An untrusted third-party submission carrying an arbitrary email address reaches a write path |
| booking email -> `prospects` row selection | An attacker-influenceable string selects which internal record gets written |
| attribution step -> HTTP response | A second, independently-failing step now sits inside a handler whose status code drives Fillout's retry behaviour |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-22 | Denial of Service | the attribution post-step's effect on the handler's status code | high | mitigate | The leads update runs first and returns exactly as today; attribution runs after it inside a `try`/`catch` that logs and sets a `failed` outcome. A non-200 would make Fillout retry a submission that already landed, which is D-7-R5's blast-radius line applied to the webhook. Enforced by the held-out failure-injection tests in Task 2 for both an async rejection and a synchronous throw, because a `try` that has stopped covering the call still reads correct. |
| T-07-23 | Tampering | booking-to-prospect match by shared mailbox or shared domain | medium | mitigate | Three controls, each closing a different hole: `isAggregatorDomain()` screens directory and social domains out of the fallback (D-7-06); the D-7-08 sent-gate means only a prospect that was actually mailed can be credited; and a candidate set that survives the gate with more than one member is refused outright rather than guessed. `booked_match_method` keeps whichever match did land auditable. |
| T-07-24 | Spoofing | the pre-existing `?secret=` query-parameter auth on this webhook | medium | accept | Unchanged by this plan, but this plan widens what that secret gates: from `leads.booked_at` to `prospects.booked_at` as well. A URL-borne secret lands in access logs and referrers. Moving it to a header or a signature would require reconfiguring the Fillout form's webhook URL, which lives outside this repo and which D-7-06 explicitly rules out changing. Recorded here so the widened blast radius is a decision rather than an inheritance; revisit alongside the Phase 8 channel work, which reopens the outbound provider configuration anyway. |
| T-07-25 | Information Disclosure | log lines added on the attribution path | low | mitigate | The route already logs the booking address once at line 59. The new lines log the outcome, the prospect id and, for the ambiguous case, a candidate count — never a second copy of the address and never a `contact_email` read from the database. Prospect ids are opaque UUIDs and are already logged elsewhere in this codebase. |
