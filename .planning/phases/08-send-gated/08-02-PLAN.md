<objective>
Build the second half of the locked two-step flow. 08-01 delivered Prepare. This delivers Mark as
sent: the immutable per-send audit record, the copy actions that sit between the two steps, and the
queue visibility that stops a prepared-but-unsent message from disappearing.

Purpose: the record is the whole point of the phase. It has to be true, which is why it is written
on an explicit human action rather than at Prepare, and why every field on it is read fresh from the
database rather than accepted from the browser.

Output: one new lib module, one new route action, the copy and mark controls in the review panel, a
sent filter and an unresolved badge in the queue, and an integration suite that proves the record is
correct and unalterable.

Implements these locked decisions from 08-CONTEXT.md:
- D-02: draft handoff is a copy-subject action plus a copy-body action. No mailto link and no .eml download.
- D-03: preparing and recording are two distinct actions. This plan builds the second one, Mark as sent, and never merges it into Prepare.
- D-04: prepared but never marked resurfaces as unresolved, prepared state is short-lived, and re-preparing re-runs the gates.
- D-05: the gate is re-run at Mark rather than trusting the Prepare result, which is what keeps suppression_checked_at honest (CMP-02).
- D-07: no legal content is authored. Counsel values are read, never written.
</objective>

`lib/send-record.ts` exports `MarkRefusal`, a string union of `not-prepared`, `prepare-stale`,
`prepared-content-changed`, `status-update-failed`; `MarkAsSentResult`, either
`{ ok: true; sendRecordId: string }` or `{ ok: false; refusal: SendGateRefusal | MarkRefusal; detail: string }`;
and `markAsSent(sb: SupabaseClient, messageId: string, preparedHash: string): Promise<MarkAsSentResult>`.

`markAsSent` runs this sequence and returns on the first failure:

1. Read `prepared_at` for the message. Null refuses with `not-prepared`. This is what makes the
   two-step flow real: nothing can be marked that was never prepared.
2. Compute the age of `prepared_at` in minutes against the current clock. Greater than
   `PREPARED_TTL_MINUTES` refuses with `prepare-stale`, and the detail line states the age and tells
   the caller to prepare again. A Prepare from days ago is not still valid.
3. Call `evaluateSendGates` again. Any refusal it returns is propagated verbatim, with its own
   refusal member and detail. This is the CMP-02 re-check: the suppression lookup that lands in the
   record is this call's, taken at mark time, not the one Prepare made.
4. Recompose the message server-side from the fresh gate context: `subject` from the context, `body`
   through `renderSendableBody` over the context's draft body, prospect id and locale. The request
   body contributes no message text at all.
5. Recompute the hash through `computePreparedHash` over the recomposed subject and body and compare
   it to the `preparedHash` argument. A mismatch refuses with `prepared-content-changed` and the
   detail states that the draft changed after Prepare and must be prepared again. This closes the
   drift where the operator copies one version and the record claims another.
6. Insert one `send_records` row. Map fields as: `outreach_message_id` from the argument,
   `prospect_id`, `resolved_email`, `resolved_email_type`, `legal_basis`, `lia_version`,
   `tw_exemption_claimed`, `first_contact_notice_included`, `is_first_contact`, `approved_by`,
   `suppression_checked_at` and `suppression_hit` all from the fresh gate context, `subject_sent` and
   `body_sent` from the recomposed message, and `sent_at` left to the column default. Catch the
   unique-violation on `outreach_message_id`, Postgres error code `23505`, and translate it to a
   refusal of `already-sent` so a double click is a clean refusal rather than a stack trace.
7. Update `outreach_messages` setting `status` to `sent` and stamping the message's sent timestamp
   column to the current ISO time. On failure return `status-update-failed` with a detail line
   stating plainly that the audit record was written and only the message status needs reconciling.

Write a comment at step 6 recording why the insert precedes the status update and is never rolled
back: the record is the legal truth of the send, the trigger makes deletion impossible by design,
and the safe direction to fail is a written record beside a stale status, never an advanced status
with no record. A row in that state stays visible through Task 3's unresolved badge.

Add nothing to `lib/send-gate.ts` except an exported helper `isPreparedFresh(preparedAt: string | null, now?: Date): boolean`
implementing the step 2 comparison against `PREPARED_TTL_MINUTES`, so the freshness rule has one
definition and the test can drive it directly.
