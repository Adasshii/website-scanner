<objective>
Hook draft generation into the scan-complete webhook as a sibling branch of the existing public-lead
path, gated by the four eligibility rules this phase locked.

Purpose: DRA-01 and D-6-05. RESEARCH Pitfall 2 is the reason this is its own plan rather than a
one-line append: the route currently rejects with 400 when the scan row has no email address, and
every prospect scan row is inserted without one. Code appended after that guard would never run for
a single bulk scan, and the failure mode is silent, because D-6-05 already treats "no draft row" as
the normal failure signal.

Output: an eligibility-gated, testable helper plus a minimal, correctly-ordered route change.

**Validation-map note:** 06-VALIDATION.md names this integration test
`app/api/internal/scan-complete/route.integration.test.ts`. It is written instead as
`lib/draft-on-scan-complete.integration.test.ts`, because the logic under test is the extracted
library helper (this repo's convention is a thin route over a tested lib, as with
`app/api/admin/shortlist/route.ts` over `lib/triage-candidates.ts`) and because no precedent exists
in this repo for constructing a `NextRequest` inside a test. Coverage is identical. Record the
rename in the SUMMARY.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scanner-service (Railway) to Next.js webhook | Bearer-token authenticated, untrusted network in between |
| scanned website content to Gemini prompt | Third-party page text reaches the model via the scan summary |
| editorial reject decision to future scans | A rejection must survive every later scan of the same prospect |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-REJ | Tampering | Rejected prospect resurrected by a later scan | high | mitigate | This plan, gate 6: `lifecycle_state = 'rejected'` is READ on every scan-complete before any generation, with a dedicated integration test asserting zero rows result. Gate 7 additionally prevents a re-scan overwriting an existing draft |
| T-06-AUTH | Spoofing | Forged scan-complete callback creating draft rows | medium | mitigate | The existing bearer-token check against `SCANNER_API_KEY` is untouched and still runs before any branch; the prospect branch is added inside the already-authenticated handler |
| T-06-PI | Tampering | Prompt injection via scanned content | low | mitigate | Generation output lands as a `draft` row that cannot leave the queue without per-message human approval (QUE-01/QUE-05); no automated downstream action exists in this phase |
| T-06-SSRF | Tampering / Information Disclosure | URLs in the draft | low | accept | Controlled in 06-04: the report link is code-constructed from `BASE_URL` and the scan id, and no URL from scanned content is embedded |
| T-06-KEY | Information Disclosure | Gemini credential | high | accept | Controlled in 06-02 and 06-04; this plan reads no credential of its own |
| T-06-BLAST | Denial of Service | A slow or failing draft breaking the public scanner's report email | high | mitigate | The prospect branch returns before the email path and cannot reach it; generation failures resolve to a failed outcome rather than throwing; `maxDuration` is raised so the function is not truncated mid-write |
