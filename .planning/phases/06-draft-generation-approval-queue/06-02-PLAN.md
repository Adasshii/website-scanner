<objective>
Close the two manual, human-only prerequisites that block end-to-end verification of this phase.
Neither can be done by an agent: one requires a credential Joshua holds, the other requires a
query against the production database through the dashboard.

Purpose: RESEARCH found the Gemini API key is missing entirely from the Next.js runtime
(`scanner-service/.env` has one; the Next.js side has none, and `app/api/health/route.ts`'s
`REQUIRED_VARS` does not list it either). The codebase convention on a missing AI key is to
return null and skip — which for this phase means "no drafts are ever generated", a silent
full-feature outage rather than a partial degradation. Separately, D-6-15's reject flag reuses
`prospects.lifecycle_state = 'rejected'`, a value declared in migration 010 but never written by
any code; since migrations here are pasted into the dashboard by hand, the live constraint gets
confirmed, not assumed.

Output: a provisioned server-side env var in both runtimes, and a recorded confirmation (or a
corrective idempotent statement, if the constraint is wrong) for the reject value.

**Schema note (read before assuming a migration is missing):** this phase authors NO migration
file. `outreach_messages` (migration 012) already carries the full `draft | edited | approved |
rejected | sent` status enum plus `approved_by` / `approved_at`, and `prospects.lifecycle_state`
(migration 010) already carries `'rejected'`. Adding a `prospects.draft_rejected` column or an
`outreach_messages.updated_at` column would be new schema for state that already exists. The
blocking manual DB step in this plan is therefore a **verification** of an already-applied
constraint, not an application of new DDL. If Task 2 finds the live constraint does NOT accept
'rejected', it becomes a real corrective DDL step — handled inside that task, still by hand in the
SQL Editor, never via `supabase db push`.
</objective>
