<objective>
Build the review surface: a fourth admin tab whose expandable rows put an editable draft beside its
scan evidence, with approve, reject, regenerate and save as per-message actions.

Purpose: QUE-01 through QUE-05, and the interaction half of D-6-13 through D-6-16. 06-UI-SPEC.md is
the binding design contract for everything in this plan; every token, class and copy string below is
lifted from it or from the existing admin components it references. Nothing here restyles the
Scans, Leads or Shortlist tabs, and nothing here introduces a component library or an icon
dependency.

The single-open expandable row is not a layout preference. It is the literal enforcement of QUE-05:
if only one row can ever be expanded, there is no code path in which two Approve buttons are
simultaneously reachable, so no bulk approve can exist even by accident.

Output: two new admin components and a four-line-shaped change to the admin page's tab wiring.
</objective>

    Left column, the editable draft:
    - A bordered subject input and a bordered body textarea, both at body size, the textarea sized
      to its content, with the accent colour on focus. Local state tracks the edited text; the Save
      action is disabled until the text differs from what came from the server.
    - Directly beneath the textarea, the Article 14 block, rendered as a read-only sibling and never
      inside the textarea. Use the left accent-bar treatment in a neutral tone so it does not read
      as an error, with a small uppercase caption reading exactly "GDPR ARTICLE 14 NOTICE" and, on
      the line below it, a smaller muted sub-label reading "Draft wording - pending counsel review",
      which reflects that `docs/legal/lia/LIA-v1.md` is itself still awaiting counsel.
    - An action row beneath that, split into two groups with clear separation between them: the
      recovery group holding "Save edit" and "Regenerate", and the decision group holding "Approve
      draft" and "Reject prospect". The two groups must not read as four equal-weight buttons.

    Actions, each addressing this one message id via a single fetch to the admin outreach route,
    each disabling its button while in flight, each calling the refetch callback on success and
    surfacing a failure the way `release-button.tsx` already does:
    - Save edit: the primary accent button, disabled until dirty. On success the row's status
      becomes edited.
    - Regenerate: a link-style accent action. When the current status is already edited, confirm
      first with exactly the copy "Regenerate this draft? Your edits will be overwritten and lost."
      When the status is draft, no confirmation.
    - Approve draft: the primary accent button in the decision group. On success the row leaves the
      pending view.
    - Reject prospect: the solid destructive button, always confirming first with the copy
      "Reject {domain}? They will not receive another draft unless you regenerate one manually. This
      does not add them to the suppression list." with the real domain interpolated. That second
      sentence is load-bearing: it disambiguates an editorial rejection from a compliance
      suppression entry, which is a different and far harder-to-reverse thing.

    Right column, the evidence pane:
    - The overall score as a badge using the same colour-band expression as the table.
    - The verdict, taken from the row as supplied by the queue library, which derives it from the
      one consolidated verdict function rather than from any stored copy.
    - A two-item row of critical and major issue counts.
    - A "Top issues" list showing the first three issues by impact, already ordered by the scan
      summary.
    - A single link reading "View full report" with a trailing arrow glyph, opening the hosted
      report in a new tab with the same target and rel attributes every other external link in this
      codebase uses.

    The cited number: apply the shared highlight token from the UI spec's Color section both where
    the number appears inside the rendered draft body and where it repeats in the evidence pane, so
    the two can be matched visually rather than re-read. Because the body is an editable textarea,

    above or beside the editor, or highlight the metric where it is restated in the evidence pane
    and label it clearly as the figure the draft is required to contain. Choose one and comment the
    choice; do not silently drop the highlight.

    This component renders exactly one draft and offers no action that reaches any other row.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser to admin API | The session secret held in sessionStorage is the only credential |
| model-generated text to rendered UI | Draft bodies originate from a model prompted with third-party page content |
| review decision to database | Approve and reject are irreversible-feeling actions taken with one click |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-BULK | Elevation of Privilege | Any view exposing more than one actionable draft | high | mitigate | The expanded-row state is a single nullable id, grep-gated against collection types and against any row-selection control; the manual check in Task 3 confirms the on-screen behaviour |
| T-06-PI | Tampering | Injected instructions surfacing in the rendered draft body | low | mitigate | The body is rendered as text inside a textarea or a text preview, never as HTML, so injected markup cannot execute; and every draft passes a human read before approval (QUE-01) |
| T-06-AC | Spoofing | Admin routes called from the browser | high | mitigate | Every fetch sends `x-admin-secret` from the existing session state, matching the Shortlist and release actions; the route re-checks it server-side |
| T-06-A14 | Repudiation | Notice edited away or hidden | high | mitigate | The notice renders as a read-only sibling block outside the textarea, grep-asserted, so it cannot be deleted through the editor |
| T-06-SUP | Tampering | Reject mistaken for a compliance suppression | medium | mitigate | The confirmation copy states explicitly that reject does not add the prospect to the suppression list |
| T-06-SEND | Repudiation | An approve action appearing to send | high | mitigate | No send affordance exists on this surface; approve moves the row out of the pending filter and stops (D-6-16) |
| T-06-SSRF | Tampering / Information Disclosure | The report link | low | mitigate | Constructed server-side from `BASE_URL` and the scan id; rendered with `rel` set on the anchor |
| T-06-KEY | Information Disclosure | Gemini credential | high | accept | No credential reaches the client; regenerate goes through the server route |
</threat_model>
