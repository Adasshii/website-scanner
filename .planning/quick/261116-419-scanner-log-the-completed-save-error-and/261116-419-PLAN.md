<objective>
Stop the silent hang where the scanner logs "[full-scan-async] Completed" but the scans row stays
in a running status forever.

Purpose: supabase-js returns a DB error instead of throwing it. The completed update in
POST /api/scan/full-async never reads that error, then clears the 15-minute timer, so a refused
save leaves the row stuck and nothing in the logs says why. Production shows this for 9 Atrium
prospects (scan 253faef3 among them). A local run of the same scan saves fine, so the production
cause is unknown; this task makes the error visible in Railway logs and turns the hang into a
failed scan. Fixing whatever makes the database refuse the save is NOT in scope.

Output: a small pure module (scanner-service/src/scan-save.ts) with unit tests written first, wired
into the full-async route and failScan. No other behaviour changes, no refactors beyond that
wiring, no Dockerfile or app/ changes.
</objective>
