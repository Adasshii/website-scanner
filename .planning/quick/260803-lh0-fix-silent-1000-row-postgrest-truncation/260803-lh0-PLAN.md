# Fix silent 1000-row PostgREST truncation in `getReportingData()`

`getReportingData()` (lib/reporting-aggregates.ts) issues two unbounded
`.select()` calls — `prospects` at line 81 and `outreach_messages` at line 88.
PostgREST caps an unbounded select at 1000 rows and returns HTTP 200 with **no
error**, so the truncation is silent. The shared local DB already holds 1006
prospects, so this is live, not hypothetical.

Two distinct consequences:

1. **`prospects` undercounts.** The Reporting tab's imported / triaged /
   scanned / contacted numbers (TRK-05) are simply wrong, and every
   delta-based assertion in the integration suite reads a delta of 0 because
   the count is pinned at the cap.
2. **`outreach_messages` gives a wrong answer, not just a small one.** The
   query orders `created_at` ASC and the fold at lines 111-119 keeps the last
   write per prospect. Truncation discards the **newest** rows, so the
   resolved latest status per prospect is wrong, and `sentGateOpen` — the
   read-time gate (D-7-13) that decides whether booked figures render at all —
   can read `false` while sends exist. That breaks the booked tally (TRK-04).

Latent since 07-02/07-03; visible only now that the table crossed 1000. It is
what failed phase 07 verification criteria 2 and 3.

## Locked approach

These are decided. Do not revisit them.

- **Paginate, do not refuse.** lib/retention.ts:90-103 handles this same cap
  with `.range(0, RETENTION_MAX_BATCH - 1)` plus a throw when the result
  length equals the cap ("refusing a truncated run"). That is right for
  retention (a partial expiry must fail loudly) and wrong here: the Reporting
  tab must keep working past 1000 rows, not go dark. Loop `.range()` until a
  short page comes back.
- **Small and local.** One helper, file-local to lib/reporting-aggregates.ts.
  No general data-access abstraction, no new dependency, no refactor of
  retention.ts to share it. There is exactly one consumer. Cite
  `RETENTION_MAX_BATCH`'s doc comment (lib/retention-constants.ts:95-105) as
  the in-repo precedent for the cap in a comment, but do not import from or
  couple to that module.
- **Stable ordering is mandatory.** `.range()` over a non-unique sort key can
  skip or duplicate rows across page boundaries. `outreach_messages.created_at`
  is not unique; `outreach_messages.id` is the uuid primary key (migration
  012, line 5) and `prospects.id` is the uuid primary key (migration 010, line
  10). Use `id` as the tiebreaker.
- **One boundary test only.** Not a suite.
